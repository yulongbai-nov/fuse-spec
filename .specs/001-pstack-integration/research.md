## Conversation decisions and simplification review

The user wants Fuse's spec-driven workflow plus pstack's engineering discipline, fewer duplicated rules, stronger verification, and predictable progression when an agent forgets. Fuse is agreed as sole workflow controller.

These criteria belong in the existing ownership and acceptance requirements rather than a new cleanup phase or permanent specialist agent. Reuse an authoritative rule where useful; do not replace small duplication with a more complex general framework. Unrelated cleanup is separate scope.

The user selected three review levels: task, integrated spec/PR, and whole codebase. Each has a maximum of two ordinary automatic repair-and-review rounds after its initial review; a run can select a lower limit. Counts belong to the reviewed task or selected spec at that level, not each finding or worker, and persist across candidate changes and resume. Later levels can pick up earlier findings within their own remaining allowance without resetting earlier counters.

The user rejected pausing the whole run at the review limit. Log unresolved findings and continue eligible unblocked work. Hold affected tasks and dependents when required checks or prerequisites are unsatisfied. For hard bugs, assign a dedicated RCA worker to reproduce, diagnose, fix within scope, and supply evidence; independent review remains required. This is an on-demand assignment, not a new permanent service. The user approved one additional diagnosis-and-fix attempt per hard blocker, including required checks and independent verification even after ordinary rounds are exhausted. Counters persist across resume and replacement agents; duplicate reports of the same underlying blocker do not create more allowances. An unsuccessful escalation leaves the blocker open while other eligible work continues. Further automatic repair of that blocker requires an operator decision.

Open findings retain one identity, blocking rationale, evidence, disposition, and history in the execution record. Later reviewers receive those findings explicitly and verify them again; omission from a new report is not resolution. This makes handoffs durable without a separate findings database or duplicate per-review lists.

## Ownership and the smallest architecture

Approved requirements, design, and task descriptions own intended behavior. One execution record owns assignments, attempts, evidence references, and accepted progress. Markdown task checkboxes reflect accepted progress; they are not independent approval stores. Evidence files prove specific observations and are referenced rather than copied into every record.

Fuse's execution phase can contain transition checks, dependency scheduling, recovery, and supervision. It can invoke model judgment for planning or ambiguous findings. Workers implement scoped changes; every code-changing task receives independent review. No additional always-thinking monitor agent is needed to notice a known missing check.

Reuse `spec-execute` as the coordination entry point for the selected-spec loop. Add only the scripts and records justified by its reliability requirements. No server, web API, application-level scheduler, or background deployment is part of the agreed execution boundary.

The guarantee is valid managed dispatch and acceptance under declared policy. Preventing unrestricted workers from modifying controller files or bypassing an external merge path would require an additional permissions boundary. The immediate forgetting problem does not require building that stronger boundary first.

Missing required tools are prerequisites to resolve, not grounds to silently mark a check inapplicable.

Independent review for code-changing tasks is agreed. Simple changes receive proportionate review; risky changes receive deeper scrutiny. This does not require a multi-model panel on every task. Rejected findings retain a rationale so automation does not blindly churn code on every suggestion.

One test or journey can support several acceptance criteria. Reuse its result references instead of running it once per requirement. Readiness does not prove behavior, and recorded pass results do not prove complete semantic correctness.

Missing, failed, unavailable, inconclusive, inapplicable, and explicitly waived checks must remain distinguishable. The user confirmed quick/auto-approve skips planning consent only; required technical verification, reviews, and merge gates remain active. ## Observed implementation boundaries

Poteto Mode is primarily an instruction-driven router and playbook runner. The parent owns the run; its agent wrapper instructs delegates to read the mode. Its plan checker verifies document structure and required fields, not whether the application was exercised or an artifact demonstrates correctness. The two reviewed pstack manifests do not register a general workflow hook. This finding concerns the reviewed snapshot, not every port or external harness.

The [baseline probes](baseline-probes.md) reproduced these Fuse helper boundaries:

- Missing spec files can produce a successful traceability result.
- A repeated task ID can overwrite an earlier task before validation.
- A checkbox is sufficient completion input for the current wave planner.
- Two tasks naming the same file can appear in one dependency wave.
- A declared dependency cycle is correctly rejected in the control fixture.

Graph independence does not establish write isolation. Reuse existing waves, concurrency cap, and TDD steps while strengthening dispatch and acceptance. The user explicitly selected continuation of unblocked work instead of wave-wide failure handling for this integration. An affected shared file, tool, or integration prerequisite can also block otherwise graph-independent work; continuation still requires validated readiness.

### Repository and host tooling snapshot

Read-only inspection on October 29, 2026 found no configured automated test suite, lint/type-check configuration, dependency manifest/lockfile, benchmark harness, or CI workflow in the Fuse source tree. Its Python helpers use the standard library; `sync_check.py` and `plan_waves.py` are workflow utilities, not substitutes for a product test suite or static analysis.

On this host, `python3` (3.15.1), Node, npm, pnpm, and uv resolve on PATH. Probes did not find pytest, Ruff, mypy, ESLint, TypeScript's `tsc`, Vitest, or hyperfine on PATH; pytest, Ruff, and mypy were also unavailable as modules in the active Python interpreter. This is a scoped availability observation, not an inventory of all environments or global installations. No tools were installed by this inspection.

Recommendation: inspect existing project setup first; use its package manager and version/lock policy, then provide minimal project-owned commands for applicable checks. CI performs platform provisioning and invokes those commands; it does not copy the test selection, lint rules, or benchmark thresholds into a second implementation. Repeated initialization should reuse or reconcile existing setup rather than append duplicate files. Performance harnesses are conditional on performance work.

Integrate with the same locked dependencies rather than separate unpinned session installs. |
| Performance regression measurement | [`pytest-benchmark`](https://pytest-benchmark.readthedocs.io/en/latest/usage.html), conditional development dependency | Reuse benchmark fixture/calibration and saved comparisons for measured helper bottlenecks. Do not build a timing/statistics harness. Workload, baseline conditions, correctness assertions, and meaningful thresholds remain project decisions; no blanket microbenchmark requirement. |

A read-only standard-library probe confirmed that `graphlib` can advance `C → D` while independent `A → B` remains blocked, and rejects a cycle. Two integration details matter: unknown predecessor IDs are automatically added as nodes by the library, so Fuse must reject them first; an outstanding blocked node can leave the sorter active without ready work, so the executor must return a checkpoint instead of busy-looping. Do not mark a failed task done merely to unblock the graph. A changed graph requires rebuilding readiness from authoritative declarations and execution records; the sorter itself is not a persistence layer.

Recommended adoption order: start with uv, pytest, Ruff, and mypy for this repo's development checks; use graphlib when strengthening scheduling; add Markdown parsing, schema validation, and sequence-testing dependencies only with their implementing changes. Consider Nox once multiple shared check sessions justify it. Add benchmarks only for an actual performance requirement. Preserve Python as the helper implementation language rather than rewrite it merely to select different tooling.

Keep Fuse-specific code small but explicit: extraction of stable requirement/design/task references, gate policy, candidate/evidence binding, finding carry-forward, two-round counters, one RCA allowance, and host dispatch glue. Standard libraries or third-party tools can supply mechanics, but cannot invent these user-approved policies. Keep `next_spec_number.py` small: its directory scan and slug normalization do not justify another dependency. Similarly, a full hosted workflow platform or extra agent orchestration framework is not justified by the selected single-spec boundary; reassess only if concrete requirements exceed the lighter approach.

The current public README promises Python 3 for bundled helpers. Adding runtime dependencies or a Python 3.9+ standard-library API changes that operational contract; design must define supported Python versions and install/bootstrap behavior before adoption. Development-only tools should not silently become requirements for every consumer of the Fuse skill. The user approved automatic restoration of missing project-local tools already selected by the repository under its package-manager and lockfile policy. New tool capabilities go through the existing design approval.

### Managing task and verification dependencies

The user asked how the DAG should cover tests and how reuse-first should be enforced. Keep authoritative task dependencies in task declarations and project check commands/prerequisites in one project-owned configuration. Derive execution readiness from those inputs and the execution record; do not hand-maintain another graph in CI YAML. Package dependency resolution remains the package manager's responsibility. Do not expand every individual test function into a Fuse scheduler node: existing runners own their internal execution.

At execution level, distinguish candidate production, required checks, and task acceptance. A task's tests depend on its candidate, not on acceptance of that same task; the latter would create a cycle. Its acceptance depends on required passing check results and review, and subsequent implementation tasks depend on acceptance. A check that needs a build or running service declares those prerequisites. Lint, types, and unit tests need not wait for one another when independent. Performance checks need a defined baseline and comparable candidate measurement, and are included only when applicable. Shared evidence can support several acceptance criteria without another run for each reference.

Prefer `graphlib` for readiness mechanics. Fuse supplies candidate/policy checks, resource eligibility, and acceptance semantics around it. A required check releases its successors only after a recorded valid outcome; task acceptance is its own validated step. Rebuild readiness when approved definitions change, invalidate stale evidence under R4, preserve failed/blocked nodes, and checkpoint when nothing can proceed. Nox is a candidate for named check sessions, not the agent acceptance controller; invoking several sessions does not establish that the Fuse dependency or review policy was satisfied. Select one owner for each prerequisite and derive local/CI execution from it.

Reuse-first is checked at planning/dispatch and all three review levels. A new nontrivial shared capability needs a brief decision in the existing design/task record: what can be reused, selected approach, and any concrete unmet need for custom code. The dispatch validator can require this record and valid references. Independent reviewers must assess whether the justification is credible and the actual code follows it; a script cannot prove that no suitable library exists. Material unjustified reinvention blocks affected acceptance and becomes one shared finding. Small routine edits do not need a new research artifact, and genuine domain-specific policy does not need a dependency merely to avoid writing code.

## Hooks and forgetting

Official [Codex hooks](https://learn.chatgpt.com/docs/hooks) and [security guidance](https://learn.chatgpt.com/docs/enterprise/security-cookbook) were read on October 29, 2026. Start/compact hooks can restore context, covered pre-tool hooks can deny calls, and stop hooks can request continuation. Hook trust, incomplete tool coverage, and failure behavior limit enforcement. A post-tool hook cannot undo completed side effects.

No hook was installed or exercised. The local CLI reported version `0.164.0`. Host-specific behavior still requires validation.

The core acceptance check must work without a hook. A worker that forgets required verification can submit a candidate, but missing evidence prevents acceptance and release of dependents. Resume restores the pending step from the execution record. It does not infer success from a worker message.

## Candidate first delivery and counterexamples

Recommendation: validate one managed execution path within the independent Fuse skill. Reuse the existing lifecycle, add task-bound methods and a small execution record, and validate readiness and acceptance. Start with configurable implementation/review profiles, not a general model ranking system.

Representative checks should establish:

1. Invalid or missing task/spec inputs reject dispatch; valid inputs remain usable.
2. Missing required evidence rejects completion and keeps dependents blocked.
3. Changed candidate code cannot reuse the previous candidate's passing result.
4. Resume reconstructs pending checks without repeating accepted work.
5. Duplicate or late reports cannot create duplicate accepted transitions.
6. Pause survives resume, and missing tools produce a visible blocker.
7. One feature and one bug fix can finish with their intended behavior demonstrated.

Orbit integration, human backlog management, and an always-available service are excluded. The selected-spec loop, three review levels, ordinary review repair limits, carry-forward findings, continuation of unblocked work, and one additional RCA attempt with independent verification per hard blocker are agreed. Change-dependent checks, repo initialization readiness, automatic restoration of selected project-local tools, tool choices through existing design approval, shared local/CI commands, stronger configured RCA profiles, and Codex-first validation are also agreed. Legacy-spec migration, in-scope task splitting/reordering, scope-change approval, and configurable execution limits are covered by R2, R3, R5, and R6. Automatic merge is approved under R4 for the selected PR when all required gates pass. The approved additions require opening or reusing a draft PR after the first pushable code job, committing and pushing each completed code job, and keeping resumable execution status aligned with the pushed candidate.
