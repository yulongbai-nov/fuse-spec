# Design: Codex-first managed execution for pstack methods

- **Spec**: 001-pstack-integration
- **Status**: approved
- **Requirements**: ./requirements.md

## Overview

Extend Fuse's existing spec workflow with a bounded, Codex-first execution controller for one selected spec. Approved requirements, design, and task files remain the source of intent and task dependencies. The controller routes eligible tasks to the agreed pstack methods, dispatches Codex workers, runs project-owned checks, records candidate-bound evidence and review findings, and accepts work only through validated transitions. It returns when the spec is complete or needs an operator decision; it is not a background service and does not depend on Orbit.

Fuse remains the sole owner of lifecycle progression, task readiness, acceptance, and finding status. Pstack contributes execution methods and verification practices inside that lifecycle. Project policy and run state will be authoritative, while a small CLI enforces mechanical prerequisites and records outcomes. Codex instructions coordinate judgment and agent conversations; optional hooks can restore or remind context but do not own acceptance gates.

## Key Design Decisions

1. **Extend the existing phases.** Keep the requirements interview, design approval, task format, stable IDs, and `spec-execute` entry point. Add managed execution behavior at the execution boundary instead of creating a second spec workflow.
2. **Keep one workflow authority and one task graph.** Fuse validates and dispatches the task dependencies already declared in `tasks.md`. Runtime readiness is derived from those declarations, the active policy, and the run record; no separate task graph or Orbit tracker is introduced.
3. **Separate judgment from enforcement.** Models may propose routes, task splits, and repairs within approved scope. Project-owned scripts validate inputs, graph constraints, check outcomes, review budgets, and allowed state transitions before those decisions release work. Each managed dispatch receives a validated assignment/attempt ID; capacity is reserved before launch, the host handle is bound after launch, and resume reconciles uncertain launches before retrying.
4. **Bind evidence to immutable candidate content.** Evidence records an immutable content identity, scope, approved intent, check configuration, and policy. Checks and reviews run in isolated worktrees pinned to that content; the controller verifies the identity again when recording results. The candidate includes relevant normalized source, task definitions, fixtures, and check inputs; execution-record and task-checkbox status metadata are excluded. Git commit/base/PR-head identifiers are recorded as provenance separately from the content digest, so a metadata-only commit does not stale evidence. New implementation content, approved intent, or check policy makes affected evidence stale. Repository-required checks still need passing results for the current PR merge candidate before merge.
5. **Keep execution bounded and resumable.** A run handles one selected spec, checkpoints authoritative progress, continues eligible work, and returns at completion, a decision boundary, or a configured limit.
6. **Prefer existing tools and project conventions.** Reuse standard-library scheduling and the repository's selected check commands where they fit. Assess any added dependencies during design, then invoke shared project-owned commands from both local execution and CI.
7. **Treat Codex as the first host adapter.** Validate Codex's actual subagent, model-selection, and command-execution capabilities. Keep shared requirements and policy host-neutral where practical, with host-specific dispatch isolated behind a small adapter.
8. **Use one publisher and one canonical run record.** Workers make each atomic job in an isolated worktree and return a task-scoped commit. The coordinator validates the assignment ID, serializes integration and pushes to each destination PR branch, and updates one canonical run record in a fetchable repository-controlled location. PR branches do not carry independent mutable record copies. A code-job push is followed by a canonical checkpoint before dependent work is released.
9. **Validate multi-PR merge candidates in order.** Derive the PR graph by collapsing the task DAG and branch relationships; reject or regroup an assignment that creates a cycle. For final reviews, build a temporary integrated candidate from the target base and all current PR heads in that order. Before each merge, also build the exact candidate formed from the then-current target base, already merged prerequisites, and the PR being merged. Run required checks and reviews against pinned candidates, and rebuild/revalidate when a merge changes a later candidate. Use one PR for tightly coupled work by default.

## Architecture

```text
Operator starts or resumes one approved spec
  -> Fuse coordinator (spec-execute with Poteto routing guidance)
       -> reads approved spec files, project policy, and run record
       -> proposes task method, worker profile, and eligible work
       -> control CLI validates the dispatch, reserves capacity, and records an assignment ID
       -> Codex adapter launches that ID and binds the returned host handle
            -> worker follows the assigned playbook in an isolated worktree
            -> worker returns an isolated task-scoped commit and evidence
       -> coordinator validates and serially integrates one job
            -> each job is a separate commit and is pushed promptly to its PR branch
            -> first pushable code commit opens or updates a draft PR
            -> coordinator checkpoints the one canonical run record
       -> checks and independent review run in worktrees pinned to the candidate ID
       -> control CLI accepts only results that still match that candidate ID
       -> coordinator continues other eligible tasks
       -> after implementation: build a temporary combined candidate from PR heads
            -> spec/PR and whole-codebase reviews assess that candidate
       -> for each merge: rebuild the current base + prerequisite PRs + target PR candidate
            -> verify current checks/reviews and merge only when R4 allows
       -> resume or /reconcile-spec loads the canonical record through the same CLI
       -> uncertain launches are reconciled by assignment ID before replacement
  -> return a completion report, or checkpoint and ask the operator at a blocker
```

It does not make product judgments or claim that a passing command proves more than the command covers.

Local execution and remote CI call the same project-owned check commands. Each completed code job is integrated as its own promptly pushed commit, with the corresponding run-state checkpoint. Only the coordinator writes to a shared PR branch or updates the authoritative run record; workers return isolated commits and evidence tagged with their validated assignment ID. The first integrated code commit opens or updates a draft PR. For multiple PRs, a temporary worktree materializes their current heads in task-dependency order for the final reviews, while the task DAG remains the only dependency graph. Evidence is bound to implementation content and approved inputs rather than status-only edits; repository checks must still pass for the current PR head. The Codex adapter uses supported subagent and model-selection tools, which are validated during implementation. Optional hooks may restore or remind an agent about its current assignment, but all allowed transitions remain validatable without hooks. The existing `/reconcile-spec` command routes managed-run reconciliation through the same CLI, so it cannot independently accept tasks or rewrite authoritative status. PR status and merge operations go through the selected repository interface and must satisfy the same candidate, check, review, and protection rules as the run record.

## Data Model / Contracts

### One canonical run record

Each managed execution has one versioned `run.json`. It is the only authority for runtime progress; approved `requirements.md`, `design.md`, and `tasks.md` remain the authority for intent and declared task dependencies; `.fuse/config.toml` is the single project-owned source for effective policy and check definitions. Task checkboxes are a projection of accepted task state and are never sufficient evidence by themselves. Check prerequisites are derived from `.fuse/config.toml` and task applicability, not maintained again in the record or CI workflow.

The record contains:

- **Identity and snapshots:** `schema_version`, `spec_id`, unique `run_id`, approved spec revision/digests, start and latest checkpoint times, and the immutable effective policy snapshot including resolved model identifiers, reasoning settings, and configured limits.
- **Assignments and task progress:** stable task IDs, validated assignment/attempt IDs, method and role profile, immutable conditional-route rationale/evidence/source route and candidate ID when applicable, launch status, host handle when known, reserved capacity, outcome, accepted candidate, and retry/repair history. An unresolved launch remains reserved until host reconciliation resolves it.
- **Candidates and evidence:** immutable candidate manifests and IDs; check/review evidence IDs, candidate IDs, check configuration/tool versions, outcomes, reviewer/assignment identity, concise result summaries, and references plus content digests for captured output artifacts.
- **Findings and decisions:** one stable finding identity per issue, affected scope, blocking decision and reason, evidence references, disposition and repair history; per-level review counters; the per-blocker RCA allowance; and operator decisions.
- **Git and PR state:** current base, integration branch, destination PR per task, commit and PR head identities, and the canonical run-state ref/revision.

Assignments, evidence, and findings are keyed by stable IDs. A retry creates a new attempt/evidence entry and does not overwrite the earlier outcome or reset review counters. The record keeps the current task status and enough history to explain transitions. It does not duplicate full agent conversations, the requirements/design/task documents, or the task/check dependency graphs. Result output is captured as an artifact and referenced by digest; if a required artifact cannot be retrieved on resume, its evidence is unavailable and the affected check or review must be rerun as R4 requires.

### Candidate and evidence contract

A candidate manifest is immutable and resolves to a content identity before checks or reviews start. It separates a `verification_inputs` object from `source_provenance`. The content digest covers the normalized source tree, approved spec inputs, effective policy snapshot, check-definition revision, and other required check inputs. Task checkbox state and run-state data are normalized or excluded. `source_provenance` records the actual tree/commit, target base, and ordered PR heads for fetching and merge guards, but is not included in `candidate_id`; a metadata-only commit therefore preserves identity when normalized verification inputs are unchanged. Evidence stores both the `candidate_id` and source provenance observed at execution, plus the check/review contract it covers. Fuse verifies the content identity again when recording the result. Changed source content, approved intent, policy, or check configuration changes the digest and makes affected evidence stale under R4. Separate evidence records may support multiple acceptance criteria, but each review level still receives an explicit outcome.

Each checkpoint is a new commit that advances the expected ref; updates are fast-forward only.
