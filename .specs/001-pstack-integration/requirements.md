# Requirements: pstack integration

- **Spec**: 001-pstack-integration
- **Mode**: requirements-first
- **Status**: approved
- **Phase**: implementation

## Purpose and authority

Combine Fuse's spec-driven lifecycle with selected pstack engineering methods. Reduce duplicated work and rules, require relevant verification, and recover progress when agents forget. Fuse is an independent spec skill.

This file is the approved product contract, including the Astra-reviewed candidate identity, canonical run record, launch recovery, and merge-candidate clarifications. [research.md](research.md) holds evidence, alternatives, and recommendations, not additional requirements. The existing Fuse interview remains in use. Requirement IDs are stable; design is approved and implementation is underway.

## Glossary

| Term | Definition |
|---|---|
| Playbook | Task-specific engineering steps used within Fuse's lifecycle. |
| Candidate | The immutable implementation snapshot being checked at a declared scope, identified with its applicable approved inputs and verification policy. Execution-record and task-progress metadata alone do not change the implementation candidate. |
| Required check | An applicable test, observation, review, or approval declared by the task's active policy. |
| Gate | A decision to permit dispatch or accept a result based on declared prerequisites and recorded outcomes. |
| Accepted task | A task whose candidate satisfies its required checks; an agent's message alone is insufficient. |
| Execution record | The authoritative record of assignments, attempts, evidence references, and accepted status. |
| Model profile | A configured role with a model choice and required tools. |
| Task | An implementation step within a Fuse spec, not an external backlog item or ticket. |
| SSOT | One authoritative definition for a fact, rule, or behavior; consumers reuse it rather than maintaining competing copies. |
| Review level | Task review checks one implementation step; spec/PR review checks the combined changes against approved intent; whole-codebase review checks broader interactions and architecture. |
| Repair round | One automatic repair attempt followed by required checks and independent re-review, after the initial review. |
| Execution policy configuration | The authoritative editable settings that define model profiles, reasoning effort, resource limits, retries, and allowed overrides for a run. |
| Blocking finding | An unresolved issue that prevents a required check, dependency, or completion criterion from being satisfied. |
| Hard blocker | A confirmed, reproducible bug that prevents required task or check progress and has an unclear root cause or has resisted an ordinary in-scope fix. |
| RCA agent | A worker assigned to reproduce a hard bug, identify its root cause, implement an in-scope fix, and supply verification evidence. |
| Agent concurrency cap | Maximum number of active subagent threads in one run, including nested agents and excluding the coordinating parent. |
| Task dependency | A prerequisite task whose accepted result is required before a dependent task is eligible. |
| Toolchain dependency | A runtime, package, or executable needed to build, exercise, or check the repository. |
| Repository initialization | Establishing or inspecting the repository's development environment and verification setup before managed implementation. |
| Atomic code job | One bounded code-changing task or in-scope repair assignment that ends at its own reviewable checkpoint. |

## Requirements

### R1: Integrate methods with traceable tasks

**User story:** As a Fuse user, I want useful pstack methods attached to my specified tasks, so that execution follows the approved intent.

1. WHEN a method is selected THEN Fuse SHALL record it with the task's stable requirement and design references.
2. WHEN the task is assigned THEN Fuse SHALL provide its scope, method, success criteria, and required checks to the worker.
3. WHEN planning an implementation task THEN Fuse SHALL choose Feature, Bug Fix, or Refactoring according to whether the task adds behavior, corrects behavior, or preserves behavior while changing structure.
4. WHEN a task needs read-only research THEN Fuse SHALL use the existing Fuse research phase; it SHALL NOT add a separate Investigation route.
5. WHEN an approved task has a measurable performance goal THEN Fuse SHALL apply the Performance Issue method and require comparable baseline and post-change evidence.
6. WHEN a task needs runtime diagnosis THEN Fuse SHALL select live-process forensics or existing-trace forensics according to the available evidence source and record the diagnosis as evidence for the next task decision.
7. WHEN an approved design question can be answered by observing an experiment THEN Fuse MAY use an isolated disposable prototype and record its observation in the existing design record; the prototype SHALL NOT decide a product preference reserved for the operator.
8. WHEN an approved requirement calls for exact visual equivalence THEN Fuse SHALL use a preserved baseline and image-diff evidence on the matching surface. This check SHALL NOT be imposed on all user-facing changes.

### R2: Give each responsibility one owner

**User story:** As a Fuse user, I want one workflow authority and clear record ownership, so that overlapping instructions do not create competing plans or status.

1. WHILE methods are integrated THEN Fuse SHALL own phase progression, dispatch, and acceptance, using one shared policy for common checks.
2. WHEN progress is reported THEN approved spec files SHALL describe intent, one execution record SHALL describe runtime progress, and task checkboxes SHALL reflect that record rather than independently establish acceptance.
3. IF an integrated method conflicts with Fuse's active scope or approval policy THEN Fuse SHALL expose the conflict before applying it.
4. WHEN multiple consumers implement the same rule or behavior THEN the change SHALL reuse or factor a common authoritative implementation where this simplifies maintenance. Similar-looking code alone SHALL NOT require an abstraction.
5. WHEN a review finding is recorded THEN the execution record SHALL own its stable identity, affected scope, blocking decision and rationale, evidence, disposition, and repair history. Later reviews SHALL reference and update that record rather than create independent copies of the same finding.
6. WHEN designing a new nontrivial shared capability THEN Fuse SHALL research existing repository capabilities and suitable maintained open-source tools or libraries before selecting an implementation. The assessment SHALL consider functional fit, compatibility, maintenance, license, and dependency cost, and cite relevant sources or repository evidence. Fuse SHALL record the selected approach, relevant alternatives, and any concrete gap requiring custom code in the existing design record. WHEN a new capability is discovered after design THEN Fuse SHALL record the assessment in the existing task or revised design record before dispatch under R3. Routine edits SHALL NOT require a separate research document. Neither a homegrown replacement nor a larger framework SHALL be introduced without a concrete need.
7. WHEN Fuse runs work THEN all model identities, reasoning efforts, concurrency values, review and RCA retry budgets, and other adopted resource limits SHALL be read from one authoritative project-level execution policy configuration rather than embedded as executable constants. Initial defaults SHALL be configurable values, not fixed limits in code. Per-run overrides SHALL use only fields and bounds allowed by that configuration. Fuse SHALL record the effective configuration and resolved model identifiers in the execution record. Changing configuration SHALL NOT rewrite the policy snapshot for an active or past run.
8. WHEN configuring a run THEN the project policy SHALL support optional elapsed-time and model-usage budgets using measurable units available on the host. These budgets SHALL be unset by default until configured. IF a configured budget is reached THEN Fuse SHALL stop launching new model work, preserve a resumable checkpoint under R5, and report the limit; Fuse SHALL NOT claim a budget was enforced when the host cannot measure it.

### R3: Validate workflow transitions predictably

**User story:** As a Fuse user, I want inspectable transition decisions, so that model judgment can remain flexible without bypassing workflow rules.

1. WHEN recorded state, resolved decisions, check outcomes, and policy are unchanged THEN Fuse SHALL produce the same allowed transitions and eligible task set. Ordering among independent tasks need not be identical.
2. IF dispatch prerequisites are missing or invalid THEN Fuse SHALL reject dispatch and identify them. These include valid task inputs and references, satisfied dependencies, and the required execution tools.
3. WHEN model judgment changes a task's method, scope, or assignment THEN Fuse SHALL record and validate that decision under the active policy before acting.
4. WHEN routing or gate rules change THEN project-owned CLI scenarios SHALL exercise representative permitted and rejected routes and transitions against the active policy. These scenarios SHALL NOT rank models or replace task-specific verification.
5. WHEN validating task dependencies THEN Fuse SHALL reject duplicate task IDs, missing dependency references, self-dependencies, and cycles before dispatch. Task dependency declarations SHALL remain authoritative; runtime readiness SHALL be derived from those declarations and accepted execution records rather than a separately maintained graph or unchecked completion claim.
6. WHEN tasks are considered for parallel execution THEN Fuse SHALL validate declared write scopes and exclusive resource use as well as dependency readiness. Conflicting tasks SHALL be serialized or isolated with explicit integration ownership; undeclared overlap discovered during execution SHALL trigger readiness re-evaluation for affected work.
7. WHEN a task or shared prerequisite becomes blocked THEN Fuse SHALL withhold affected work and continue other eligible tasks within the concurrency limit. A historical wave boundary alone SHALL NOT prevent otherwise eligible progress. Dependency or scope changes SHALL be recorded and revalidated before further dispatch.
8. WHEN dispatching implementation of a new nontrivial shared capability THEN Fuse SHALL require the reuse assessment defined in R2. Missing assessment SHALL block that assignment rather than unrelated work. Automated validation SHALL establish the assessment's presence and references, while independent review under R4 SHALL assess its substance.
9. WHEN an executor splits or reorders work within approved scope THEN Fuse SHALL record the resulting task and dependency changes, preserve requirement/design traceability and applicable checks, and revalidate readiness before dispatch. IF the change requires expanding approved scope or waiving a gate THEN R6's operator-decision policy SHALL apply.
10. WHEN code-changing tasks are assigned to PRs THEN Fuse SHALL record one current destination PR per task and MAY group tasks across one or more PRs according to approved scope and validated task dependencies. By default, Fuse SHALL keep tightly coupled or dependent tasks together and split independent, reviewable slices only when separate PRs help parallel work or review. Fuse SHALL reuse a compatible PR or open a new one using repository conventions. PR dependency and merge order SHALL be derived from the task DAG and branch relationships rather than maintained in a second graph. The derived PR merge graph SHALL be acyclic; if task-to-PR assignments create a cycle, Fuse SHALL regroup the affected work or hold it for the operator. IF a task cannot be safely assigned within scope or repository constraints THEN Fuse SHALL hold affected work and ask the operator.
11. WHEN the first atomic code job produces a pushable commit and the repository supports pull requests THEN Fuse SHALL open or reuse a compatible draft PR promptly, before waiting for remaining implementation tasks or final reviews. The PR SHALL identify the selected spec and current candidate. If draft PR creation is unavailable or fails, Fuse SHALL record the blocker and follow R6.
12. WHEN an atomic code job reaches a reviewable checkpoint THEN Fuse SHALL create a task/job-scoped commit and publish it promptly to its assigned PR branch. Each completed code-changing job SHALL have a distinct commit; Fuse SHALL NOT hold completed jobs solely to batch commits. One coordinating integration owner SHALL serialize writes and pushes to each shared PR branch; workers SHALL return isolated task-scoped commits rather than directly mutate a shared PR branch. A failing check MAY be visible on a draft PR but SHALL NOT satisfy acceptance under R4. IF branch conflicts or repository controls prevent a safe push THEN Fuse SHALL preserve the work, record the blocker, and follow R6; it SHALL NOT overwrite another worker's changes.

The generation of a review verdict or planning proposal is not deterministic. This requirement concerns validation of recorded outcomes, not a guarantee of semantic correctness.

### R4: Accept results using current evidence

**User story:** As a Fuse user, I want acceptance supported by relevant evidence, so that an unsupported completion claim does not release dependent work.

1. WHEN a task is prepared THEN Fuse SHALL declare its applicable checks, pass criteria, and any required reviewer or operator decision. One run may support multiple criteria without duplicated execution or records.
2. WHEN acceptance is requested THEN Fuse SHALL require passing results for the candidate and approved task/spec and policy versions being accepted. Fuse SHALL resolve the candidate to an immutable content identity before a check or review begins, run it against that pinned snapshot, and verify the same identity when recording the result. Candidate identity SHALL hash normalized verification inputs, including relevant source content, approved intent, policy, and check inputs; Git commit, branch, base, and PR-head identities SHALL be recorded separately as provenance. A metadata-only commit SHALL NOT stale evidence when normalized verification inputs are unchanged. An author report or checked box alone SHALL NOT satisfy this gate.
3. IF a required result is missing, failed, unavailable, or inconclusive THEN Fuse SHALL withhold acceptance and name the gap, unless a waiver permitted by the active policy is explicitly authorized and recorded.
4. WHEN the implementation candidate, approved intent, or verification policy changes THEN earlier evidence for the affected scope SHALL be treated as stale until required checks are rerun. Execution-record and task-progress metadata alone SHALL NOT change the implementation candidate. Selective reuse is not required for the first release.
5. WHEN reporting results THEN Fuse SHALL distinguish executed checks from reviewer or human assessments. Quick/auto-approve MAY skip planning consent only; it SHALL NOT waive required technical checks, reviews, or PR merge gates. Any separate technical waiver SHALL require the authorization and record permitted by the active policy.
6. WHEN a task changes code THEN acceptance SHALL require a review of its current candidate by a reviewer that did not implement that candidate. Review depth SHALL be proportional to the change's risk and complexity.
7. WHEN reviewing code THEN the reviewer SHALL assess correctness and maintainability, including whether comments are accurate and necessary, unnecessary complexity, duplicated rules, dead code, and opportunities for useful shared code. Proposed cleanup SHALL remain within the task's scope or be recorded as separate work.
8. WHEN all implementation tasks are accepted THEN Fuse SHALL obtain independent reviews at both the integrated spec/PR and whole-codebase levels, in addition to task-level reviews. Spec/PR review SHALL assess the combined changes against approved requirements, design, and required checks. Whole-codebase review SHALL examine broader cross-component behavior, architecture, shared rules, and duplication. When a spec uses multiple PRs, the integrated candidate SHALL combine the current PR heads with their target base in validated merge order and record each included head identity. Each review SHALL state its coverage and limitations. Shared evidence and findings SHALL be reused without duplicating checks while retaining an explicit outcome for each level.
9. WHEN reporting spec completion or merge readiness THEN Fuse SHALL include both final review outcomes and unresolved findings. The same current reviews SHALL satisfy both checkpoints without duplicate execution; a changed candidate or review context SHALL require renewed review under criterion 4. Before merging each PR, Fuse SHALL validate the exact merge candidate formed from the current target base, already merged prerequisite PRs, and that PR's current head; required checks and reviews SHALL cover that candidate. If a prior merge or base update changes a later PR's candidate, Fuse SHALL rebuild it and refresh affected evidence before merge. WHEN a PR's current head and merge candidate pass every applicable required check and all three review levels, have no unresolved review findings, and the repository reports it mergeable THEN Fuse SHALL merge it after any prerequisite PRs, using a provider-supported merge queue or atomic base/head guard that binds the actual merge to the validated candidate. IF the provider cannot enforce that binding THEN Fuse SHALL withhold automatic merge and report a blocker for operator decision; a last-minute status read alone SHALL NOT satisfy the guard. WHEN a required check is pending THEN Fuse SHALL NOT merge and SHALL continue status monitoring under R6. IF a required check fails or a finding remains unresolved THEN Fuse SHALL first follow R6's in-scope repair and retry policy; if the problem remains after the configured allowance, or a check is unavailable or inconclusive, or the repository requires human action, Fuse SHALL report the blocker and request the needed operator decision. Fuse SHALL NOT bypass repository protections or required approvals.
10. IF review finds an unrelated pre-existing issue THEN Fuse SHALL record it as a follow-up rather than automatically expand scope. Findings affecting the spec's correctness or exposing critical security risks SHALL block completion; any required scope expansion SHALL follow R6's operator-decision policy.
11. WHEN a later review begins THEN Fuse SHALL provide relevant unresolved findings from earlier reviews for explicit re-verification and disposition. Absence from a new review report SHALL NOT close a finding. Resolution or dismissal SHALL require current supporting evidence or a recorded rationale; repair SHALL use the applicable budget under R6.
12. IF a finding is non-blocking under the active acceptance policy THEN Fuse SHALL retain it as open or deferred and permit otherwise eligible progress. Logging a failed required check SHALL NOT satisfy it or release work that depends on it.
13. WHEN checks are selected THEN code changes SHALL require relevant tests and applicable available lint/static/type checks; user-facing behavior changes SHALL require relevant real-surface verification; performance claims SHALL require comparable baseline and candidate measurements under recorded conditions. Irrelevant checks SHALL NOT be mandatory; missing required tooling SHALL be handled under R8 rather than silently treated as inapplicable.
14. WHEN reviewing a new nontrivial shared capability THEN the independent reviewer SHALL verify the R2 reuse assessment against the actual change and challenge unnecessary custom equivalents or overlapping dependencies. Material unjustified reinvention SHALL block acceptance of affected work until reuse is implemented or a concrete justification is recorded and accepted under the active policy. The same criterion SHALL apply at task, spec/PR, and whole-codebase review, using shared findings rather than duplicate checklists. A dependency's mere existence SHALL NOT prove it fits the requirement.

### R5: Restore work without trusting agent memory

**User story:** As a Fuse user, I want task recovery from the execution record, so that lost context does not invent progress or repeat accepted work.

1. WHEN work begins or resumes THEN Fuse SHALL reconstruct the active assignment and remaining checks from its records, using R3 for dispatch and R4 for acceptance.
2. WHEN a duplicate or outdated worker report arrives THEN Fuse SHALL avoid a duplicate accepted transition and prevent it from accepting a newer candidate or replacement attempt.
3. WHEN work is paused or cancelled THEN Fuse SHALL preserve that state across resume; callbacks SHALL NOT override it.
4. IF an optional hook is absent or fails THEN R3 and R4 SHALL still govern managed execution, and reduced hook support SHALL be reported.
5. WHEN Fuse first adopts an existing spec with checked tasks but no execution records THEN it SHALL preserve the approved spec files and import those checkboxes only as reported legacy progress. Fuse SHALL derive applicable checks from the approved task/spec and project policy, bind them to the current candidate, and require current passing evidence under R4 before such a task can release dependents. A checkbox alone SHALL NOT establish acceptance.
6. IF a legacy task lacks enough approved detail to determine its scope or required checks THEN Fuse SHALL preserve its recorded progress, identify the missing information, and hold only affected work for clarification; Fuse SHALL NOT silently rewrite the approved requirements, design, or task scope.
7. WHEN execution progress changes THEN Fuse SHALL persist a resumable checkpoint in one repository-local execution record, including spec/run identity, effective policy snapshot, task and finding state, retry counters, and current branch, commit, and PR/head identities. Fuse SHALL keep one canonical, fetchable copy for the run in a repository-controlled durable location and SHALL NOT maintain independently mutable execution-record copies on PR branches. The coordinating owner SHALL serialize record updates and checkpoint after each atomic code job, required check or review result, accepted transition, blocker, and operator decision. After each code-job push, the canonical record SHALL be synchronized with its exact commit and PR/head identity before dependent work is released. WHEN resuming or reconciling THEN Fuse SHALL load that canonical record and compare it with the approved spec files, pinned Git candidates, and PR heads, and report discrepancies before dispatch. A task checkbox or execution record alone SHALL NOT override a mismatch.
8. WHEN a worker launch is prepared THEN Fuse SHALL persist its unique assignment/attempt ID and reserve its concurrency capacity before invoking the host. After launch, Fuse SHALL bind the host invocation handle to that ID. IF a run resumes with an uncertain launch outcome THEN Fuse SHALL query or reconcile the host using the ID/handle before retrying; it SHALL NOT launch a duplicate or release the reservation while the outcome is unknown. IF the host cannot resolve the outcome THEN Fuse SHALL hold that assignment and its dependents, report the blocker, and continue unrelated eligible work. Nested launches SHALL use the same reservation and concurrency accounting.
9. WHEN a run is started or resumed THEN Fuse SHALL load the exact run ID if one is provided; otherwise it SHALL select the sole active run for the selected spec. IF discovery without an explicit ID finds multiple active runs THEN Fuse SHALL report the ambiguity and SHALL NOT silently create or select another run. WHEN the selected run has an unresolved launch THEN Fuse SHALL reconcile it under R5.8, retain that assignment's capacity reservation, and continue unrelated eligible work within remaining capacity. A new run SHALL require an explicit start after prior runs are terminal. Run lifecycle status SHALL be persisted as running, paused, cancelled, or completed and SHALL survive resume.

### R6: Run a bounded execution loop for one spec

**User story:** As a Fuse user, I want execution to coordinate a selected spec until it finishes or needs my decision, so that useful work continues without requiring an always-running service.

1. WHEN execution is requested THEN Fuse SHALL operate on the selected spec's eligible tasks under R3, R4, and the active approval policy.
2. WHILE authorized work is actionable THEN Fuse SHALL continue that run without asking for renewed permission for each already-authorized step.
3. WHEN every required task has been accepted and both final review levels required by R4 have met the active acceptance policy THEN Fuse SHALL report completion and return control.
4. IF no allowed next action remains because work is blocked, a required decision is pending, or an execution limit is reached THEN Fuse SHALL report the condition, preserve resumable state under R5, and return control.
5. WHEN the run ends THEN Fuse SHALL NOT keep invoking models or automatically start unrelated specs.
6. WHEN a required check fails or review identifies a valid finding within approved scope THEN Fuse SHALL arrange repair, rerun the required checks for the changed candidate under R4, and obtain another independent review without asking for permission for each repair round.
7. IF repair requires changing approved scope or waiving a required gate THEN Fuse SHALL preserve the unresolved findings and request an operator decision for that action while continuing other authorized unblocked work. A proposed finding judged invalid SHALL be recorded with its dismissal rationale rather than automatically changing code.
8. WHEN automatic repair is needed at the task, spec/PR, or whole-codebase review level THEN Fuse SHALL apply the configured ordinary repair-and-review limit after that level's initial review. The initial configuration SHALL set the agreed default maximum of two rounds per level and MAY let a run select a lower value. The count SHALL belong to the reviewed task or selected spec at that level and SHALL NOT restart for each finding, replacement worker, changed candidate, or resumed run. A later review level MAY pick up an earlier finding within its own remaining allowance; the earlier level's counter SHALL remain unchanged. Merely relabeling an attempt SHALL NOT create a new allowance.
9. WHEN a review's repair limit is reached THEN Fuse SHALL log remaining findings and their dispositions and continue eligible unblocked work rather than pause the entire run solely because that limit was reached. Blocked tasks and their dependents SHALL remain ineligible until their prerequisites are satisfied.
10. WHEN a confirmed, reproducible bug blocks a required task or check and its root cause is unclear or it has resisted an ordinary in-scope fix THEN Fuse SHALL assign a dedicated RCA agent to reproduce it, identify the cause, and implement an in-scope fix with verification evidence. The assignment SHALL reference the existing finding and preserve review counters. Changes SHALL still require current checks and independent review under R4.
11. WHEN RCA escalation is used THEN Fuse SHALL apply the configured additional diagnosis-and-fix attempt limit per hard blocker, including required checks and independent verification of the resulting candidate even if ordinary review rounds are exhausted. The initial configuration SHALL set this limit to one attempt per blocker. This separate allowance SHALL NOT reset ordinary review counters, renew on resume or agent replacement, or multiply for duplicate reports of the same underlying blocker. IF the configured allowance is exhausted or verification remains unsuccessful THEN Fuse SHALL retain the blocker, stop automatic repair of that blocker, and continue other eligible work; further repair SHALL require an operator decision.
12. WHEN clarification or coordination would help resolve an issue THEN Fuse MAY route focused follow-up exchanges among the relevant agents within the active resource limits. It SHALL record resulting decisions, unresolved questions, and evidence references in the execution record, and apply the existing dispatch and acceptance rules. An agent conversation SHALL NOT itself establish acceptance or override scope and review policies. IF the host cannot support an exchange THEN Fuse SHALL report the limitation and use available coordination paths under the same policy.
13. WHEN launching subagents THEN Fuse SHALL enforce the configured concurrency cap across the full nested agent tree, including reserved but not yet confirmed launches. The initial configuration SHALL default to the greater of five or the number of independent eligible task workers ready at dispatch when ordinary workers use Luna at Max, and three for other worker profiles. Count ready tasks once; do not count check jobs or descendants as additional task workers. The user MAY configure a different cap or a per-run override within the configured policy and host limits. The coordinating parent SHALL NOT count toward the subagent cap. A worker SHALL NOT evade the cap by launching descendants.
14. WHEN a configured elapsed-time or model-usage budget is reached THEN Fuse SHALL checkpoint the run and return control without launching further models; independent checks that require no model MAY finish only when they remain within the configured execution policy. Resuming SHALL use the saved state and a newly validated run budget, without resetting review or RCA attempt counters.

### R7: Choose suitable workers and models

**User story:** As a Fuse user, I want configurable role choices and explainable adaptation, so that tasks receive suitable capabilities without an unnecessarily elaborate selection system.

1. WHEN assigning a worker or reviewer THEN Fuse SHALL choose from configured role profiles whose required tools and model can be used on the execution host. Unsupported cognitive capability probes are not required.
2. IF the configured choice is unavailable THEN Fuse SHALL use only a policy-permitted fallback or report a blocker. Selection, fallback, and escalation SHALL be recorded under R3.
3. WHEN observed complexity warrants reassignment or replanning THEN the Fuse executor SHALL act only within the configured autonomy and resource limits, preserving the task's required checks.
4. WHEN a hard blocker needs RCA escalation THEN Fuse SHALL assign Astra with Max reasoning where supported to diagnose and repair it within the configured RCA allowance. Selection SHALL validate the actual model, reasoning setting, tools, and host availability, and record the reason for escalation. Stronger-model selection SHALL NOT increase the repair allowance or bypass independent verification; any nested agents SHALL count toward the run's concurrency and resource limits.
5. WHEN assigning an ordinary worker THEN Fuse SHALL prefer the latest Luna model available to the host with maximum supported reasoning effort. Fuse SHALL resolve and record the actual model identifier and reasoning setting for the run. IF the preference is unavailable, Fuse SHALL report the limitation or use only an explicitly permitted fallback; it SHALL NOT silently claim the preferred profile was used.
6. WHEN assigning a regular independent reviewer THEN Fuse SHALL prefer the latest Sol model available to the host with Extra High reasoning (`xhigh` where that is the host setting). Fuse SHALL record the actual model and reasoning setting; if unavailable it SHALL report the limitation or use only an explicitly permitted fallback. This concrete reviewer profile SHALL govern in place of abstract model-tier arithmetic; reviewer independence under R4 still applies.
7. WHEN an Astra RCA agent changes code THEN Fuse SHALL obtain an additional independent review of that fix using a separate Astra agent with Max reasoning where supported, even if another review level already assessed the change. This review SHALL verify the RCA result and its evidence under R4. If Astra or Max is unavailable, Fuse SHALL report the limitation and use only an explicitly permitted fallback.

### R8: Establish reproducible repository and verification readiness

**User story:** As a Fuse user, I want dependencies and check commands established at repository initialization, so that local workers and remote CI verify the same intended behavior without duplicated workflow logic.

1. WHEN a repository is initialized or first adopted THEN Fuse SHALL inspect its languages, dependency manifests and lockfiles, runtime constraints, existing scripts, CI/actions, and applicable test, benchmark, lint, static-analysis, and type-check tooling. Fuse SHALL distinguish configured tooling from tooling that can actually run in the active environment and report missing prerequisites.
2. WHEN setup is needed THEN Fuse SHALL reuse the repository's selected package manager, version constraints, lockfiles, and project-scoped environment where available. An unconfigured repository SHALL receive a minimal proposed setup appropriate to its stack; a competing package manager or duplicate dependency manifest SHALL NOT be introduced merely for Fuse.
3. WHEN defining verification THEN project-owned commands and configurations SHALL own check logic, thresholds, and applicable tool versions. Local execution and remote CI/actions SHALL invoke those same entry points rather than independently implement their rules. Environment-specific provisioning, credentials, triggers, caching, and artifact transport MAY differ and SHALL remain explicit.
4. WHEN a new verification setup is established THEN Fuse SHALL exercise its applicable commands and report actual outcomes before declaring it ready. A configured executable name or generated workflow alone SHALL NOT establish readiness; unavailable remote execution SHALL remain explicitly unverified.
5. IF a required project-local tool or dependency is missing but already selected by the repository THEN Fuse SHALL automatically attempt to restore it using the established package manager, version constraints, and lockfile policy, and verify availability. IF restoration fails or the existing selection is incompatible THEN Fuse SHALL record the gap and block affected work; other eligible work MAY continue under R3. Benchmark tooling SHALL be required for relevant performance work rather than every repository.
6. WHEN dependency or verification configuration changes THEN Fuse SHALL update its authoritative project configuration and revalidate affected readiness and evidence under R3 and R4. Repeated initialization SHALL reuse the established setup and SHALL NOT append duplicate scripts, configurations, or workflow jobs.
7. WHEN preparing required verification THEN Fuse SHALL derive check prerequisites from the authoritative project check configuration and task-specific applicability, and validate them under R3. Checks SHALL have stable identities, commands or procedures, required inputs, pass criteria, and current candidate-bound outcomes. Only actual prerequisites SHALL serialize checks; independent checks MAY run in parallel within resource limits. Missing, failed, or stale prerequisites SHALL withhold dependent checks and acceptance under R4 while unrelated eligible work continues. Local and remote workflows SHALL consume the same definitions rather than maintain competing dependency declarations.
8. WHEN a required capability has no established toolchain selection THEN Fuse SHALL investigate project needs, existing conventions, applicable primary documentation, and relevant practices from established open-source projects before proposing a minimal toolchain. The proposal SHALL record evidence and tradeoffs under R2, including compatibility, maintenance, license, dependency cost, and suitability for local and CI use. Examples SHALL be adapted to the repository rather than copied merely because they are popular. Fuse SHALL distinguish research from locally verified availability.
9. WHEN new tool selections are proposed in design THEN Fuse SHALL present them through the existing design approval under the active Fuse approval mode rather than require a separate approval for each tool. Later changes SHALL follow the existing scope and design-change policy under R3 and R6.
10. WHEN the integration is implemented THEN Fuse SHALL validate the Codex execution path first, including its supported subagent communication, model/reasoning selection, and check invocation. Shared requirements, task formats, and skill instructions SHALL remain host-neutral where feasible; host-specific behavior SHALL be isolated behind existing or minimal adapters and declared per host. Support for other advertised hosts SHALL be validated separately rather than inferred from the Codex result.
11. WHEN an applicable verification check has a project script or CLI entry point THEN Fuse SHALL prefer invoking that command directly and capture its exit status, output, and candidate/configuration context as evidence. Local and remote environments SHALL call the same project-owned command where feasible. Agents SHALL review result summaries and evidence rather than repeatedly reasoning through checks already machine-verified; model involvement SHALL be reserved for interpreting failures, semantic review, or checks that lack an executable procedure. A passing command SHALL support only the criteria it actually tests.

## Non-functional boundaries

- The enforcement claim covers dispatch and acceptance through Fuse. Preventing every out-of-band worker action is a separate assurance level, not assumed by this draft.
- Existing approval modes, task IDs, dependency waves, and the TDD loop should be reused. Exact persistence format and host adapter design remain design choices.

## Open decisions

No unresolved decisions from the requirements interview remain. R1–R8, the PR/checkpoint additions, Astra-reviewed clarifications, and the design contract are approved. Task-plan generation, implementation, and verification are underway.

## Out of scope

Orbit integration, task-tracking panels, human backlog management, always-available services, and multiple concurrent coordinators are outside this feature. The sustained metric-optimization Hillclimb playbook is deferred. Model ranking, mandatory formal verification for every ordinary task, separate monitoring-agent services, and merge bypasses are also outside scope. Automatic merge is allowed only under R4.
